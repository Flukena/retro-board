# Google sign-in rollout (pending owner approval)

Status: prepared on branch `feat/google-sign-in`, nothing deployed. Every step
marked PENDING OWNER changes production and needs explicit approval
(`AGENTS.md` "Needs owner approval").

## What ships

- Optional "Sign in with Google" on the landing page and an account menu
  (sign out, sign out everywhere, delete account). Scopes: `openid email profile`.
- Relay endpoints under `/yjs/api/auth/google/*` and `/yjs/api/account`, with
  accounts stored in the relay LevelDB (`yjs_data`), keyed by Google `sub`.
- Updated privacy text (11 locales) and backup verification that checks account
  records.
- Guests are unaffected: boards, links, passwords and the Public Wall work
  exactly as before. Sign-in is off unless the relay has all three Google
  variables and a non-empty `YJS_ALLOWED_ORIGINS`. The Public Wall relay
  (`yjs-public`) never gets Google variables and has sign-in structurally off.

Notes:

- `relay_egress` is a normal (non-internal) bridge network. It gives `yjs`
  **general outbound access**, not only `oauth2.googleapis.com`. A hostname
  filter is not used because the relay trusts Google's `id_token` by TLS alone
  (OIDC Core 3.1.3.7, token endpoint over HTTPS), and Compose cannot filter by
  hostname anyway. Cost: a compromised relay could also reach the internet.
  Mitigations that stay: no published ports, `read_only`, `cap_drop: ALL`,
  `no-new-privileges`, only the relay code makes the Google call.
- `yjs-public` is defined with `<<: *relay-service`, so it would inherit the new
  `networks` list. The diff adds an explicit `networks: [app_internal]` there
  to keep it without egress. Its `environment` list is its own, so it inherits
  no Google variables. After the change, confirm with `docker inspect` (step C5).
- `YJS_ALLOWED_ORIGINS=https://retroroom.party` is a literal in the compose file
  (lines 59 and 120), not read from `.env`, so it is non-empty. The Google
  variables are passed through from `.env`; the owner adds
  `GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET` there (never in the
  repo). `YJS_ACCOUNT_SESSION_SECRET` is optional; without it the relay creates
  and persists `/data/.account-session-key` in `yjs_data`.
- The running containers use `miro-release-*` image tags, so the owner's deploy
  flow retags builds. The candidate images below use other names; deploy must use
  images built and scanned the way you normally release.

## 4. Post-deploy smoke check (owner)

1. Signed out: `curl -si https://retroroom.party/yjs/api/account` returns
   `401` (not 404 or 5xx).
2. Open https://retroroom.party in a browser, choose Sign in with Google, complete
   consent. You return to the page you came from and the account menu shows you.
3. DevTools, Application, Cookies: the account cookie has `Secure`, `HttpOnly`,
   and `Path=/yjs/api`. The Set-Cookie response on the callback shows the same
   flags.
4. Reload: still signed in.
5. In a second browser (or private window) sign in as the same account, then use
   **Sign out everywhere** in it. The first browser is signed out on its next
   action or reload.
6. Sign in again, choose **Delete account**, confirm. You are signed out and the
   same Google login creates a fresh account.
7. Open an existing board (and the Public Wall) as a guest: loads, edits sync,
   an image loads. Existing room links still work.
8. Relay logs show no `GOOGLE`/token/cookie content: `docker logs <yjs-container> | tail`.

## 5. Rollback

1. Remove the four Google lines from the `yjs` environment and the
   `relay_egress` network entries (the `yjs` `networks` item, the `yjs-public`
   override, and the top-level network), or revert the compose commit.
2. `docker compose -f docker-compose.prod.yml up -d --no-build` (recreates `yjs`;
   to return to the previous image, retag the previous `miro-release-*` image
   as the compose image first).
3. Sign-in is then off and `yjs` has no egress again. Accounts already created
   stay in LevelDB (`acct:`, `sub:`, `email:` keys). Older relay code never reads
   those keys; a downgrade run against a copy was not tested, so treat "harmless"
   as expected, not proven. No cleanup is needed. If data looks wrong,
   restore the C1 backup (owner approval required).
